# Gemma 4 12B support for r4dx -- design and task plan

Branch `gemma4` (from `main` at `9063730`). Written 2026-10-01. This is a **design only**: no source
file was edited, no GPU workload was run and no package was installed while writing it. Where it says
MUST, do exactly that; anything not covered is a question for the user. Items tagged **UNVERIFIED**
were inferred or read from a summary and must be settled by task M0-5 (reading the HF modeling code)
before the code that depends on them is written.

## Summary

r4dx today runs exactly one architecture, the Qwen3.5 hybrid (GDN + full attention), with no arch
dispatch. This plan adds `huihui-ai/Huihui-gemma-4-12B-it-abliterated` (`gemma4_unified`, 48 layers,
5 sliding : 1 full attention, tied 262144-vocab embedding, sandwich norms, GeGLU, logit softcap) as a
second architecture behind the existing `TextModel` interface, without touching the Qwen hot path.

The plan has four design sections (text model and kernels, converter and quantization, tokenizer and
server, validation and drafter), a critique that resolves their conflicts, and a milestone task list:
M0 setup and reference data, M1 text at TP=1 with the KL gate and server, M1b TP=2, M2 vision, M3 audio,
and a parallel non-blocking drafter track D. The largest technical risk is the full-attention
`head_dim 512 / gqa 16` kernel; the largest schedule item is the Gemma-specific quantization stack.
Every GPU step is a command handed to the user.

## 1. Agreed decisions (condensed)

- **Target.** Huihui-gemma-4-12B-it-abliterated (`gemma4_unified`, `Gemma4UnifiedForConditionalGeneration`,
  single `model.safetensors`, 23.9 GB bf16). Chat template and `tokenizer_config.json` come from
  current `google/gemma-4-12B-it`.
- **Structure.** Separate `GemmaModel` / `GemmaTpModel` behind `TextModel`, dispatch on config
  `model_type`; the Qwen hot path stays untouched.
- **Order.** Text, then vision, then audio; no video. TP=1 first; TP=2 after TP=1 passes KL (global
  single KV head replicated, 8 sliding KV heads split 4 per rank; sharding must allow tied embeddings).
- **Context.** Native 262k; sliding layers use a 1024-token ring KV.
- **Quantized from the start.** Trellis (port `tools/reference` hessian_capture / trellis_quant to Gemma
  module names). Residual rotation is generalized now to any hidden size (3840 = 15 x 256; 5120 is
  hard-coded in `src/model/rotation_meta.h` and `src/convert/include/r4dx_convert/rotation.hpp`).
  Calibration data is generated by Huihui-Gemma itself.
- **fp8 KV from the start.** Existing fp8 e4m3 paged cache with static per-(layer,head) descales; needs
  Gemma calibration.
- **Tokenizer.** Extend the in-house `src/tokenizer/bpe_tokenizer.cpp` (byte_fallback, Replace
  normalizer, newline-run rule); validate with `tests/tokenizer/golden_test.cpp` +
  `tools/tok_ref/gen_golden.py`; microbench vs HF tokenizers.
- **Server in M1.** Per-model pluggable reasoning splitter and tool-call parser.
- **Gate.** Per-layer bf16 goldens vs HF (rung 3) + teacher-forced KL vs the **fp32 truth**, noise-relative,
  on `kl_corpus/chat_gemma.json` (section 9.9-9.11; supersedes the earlier "mean KL <= 0.01, top-1 >= 95% vs
  bf16 HF"), plus greedy smoke.
- **Drafter (parallel, non-blocking).** Convert `z-lab/gemma4-12B-it-DFlash` (DFlash v1) into the
  DFlash2 container with identity conv and zero selector, measure acceptance, then warm-start fine-tune
  conv + selector on 20-100K Huihui samples with an own plain-PyTorch trainer (target bf16 GPU0,
  trainer GPU1).
- **Environment.** New ROCm Python venv with transformers >= 5.10; the existing Python312 env is left alone.
- **GPU policy.** Every GPU step is handed to the user as a command; agents never run GPU work.

## 2. Architecture facts (HF config / modeling)

- hidden 3840, 48 layers, 16 q heads; pattern 5 sliding : 1 full (full at layers 5, 11, ..., 47).
- **Sliding:** head_dim 256, 8 KV heads (GQA 2), window 1024, RoPE default theta 1e4 full-rotary.
- **Full:** head_dim 512, 1 KV head (GQA 16), `attention_k_eq_v` (no v_proj; V = raw k_proj output ->
  v_norm (RMSNorm, no weight); K = k_proj -> k_norm -> rope). RoPE "proportional", theta 1e6,
  partial_rotary_factor 0.25: `inv_freq[i] = 1/base^(2i/head_dim)` for i < 64 with `head_dim` = 512 in the
  exponent's denominator (the full width, not the 128 rotated dims), remaining frequencies zero (NoPE dims),
  rotate-half layout (pairs `i, i+256`). q_norm/k_norm are RMSNorm with weight.
- Attention scaling = 1.0 (no 1/sqrt(d)); no attention softcap.
- RMSNorm is `x*rsqrt(mean(x^2)+eps)*weight` in fp32 (NOT 1+w), eps 1e-6.
- Decoder layer: input_layernorm -> attn -> post_attention_layernorm -> +res; pre_feedforward_layernorm
  -> MLP -> post_feedforward_layernorm -> +res; then hidden *= `layer_scalar` (per-layer buffer).
- MLP GeGLU: `down(gelu_tanh(gate(x)) * up(x))`, intermediate 15360.
- Embedding scaled by sqrt(3840) (multimodal embeds not scaled). Tied lm_head, vocab 262144, final
  logit softcap `tanh(x/30)*30`. bos 2, pad 0, eos 1 / end-of-turn 106.
- **Vision (12B, no encoder):** 16 px patches merged 3x3 -> 48x48x3 HWC raster = 6912 values; rescale
  1/255, no mean/std; aspect-preserving resize with h*w <= 280*9*256 floored to a multiple of 48.
  Embedder: LayerNorm(6912, eps 1e-5, bias) -> Linear(6912->3840, bias) -> LayerNorm(3840) ->
  + pos_embedding[x,0] + pos_embedding[y,1] (shape [1120,2,3840]) -> LayerNorm(3840) (pos_norm) ->
  RMSNorm no weight eps 1e-6 -> Linear(3840->3840, no bias). <= 280 soft tokens. Image tokens are
  bidirectional within a contiguous image block on the **sliding layers only**; full layers stay causal
  (settled by M0-5: docs/gemma4-semantics.md section 2).
  Ids: image 258880, boi 255999, eoi 258882.
- **Audio (12B):** 16 kHz raw waveform, right-pad to a multiple of 640, [n,640] -> RMSNorm(640, no
  weight) -> Linear(640->3840, no bias); causal; max 750 tokens. Ids: audio 258881, boa 256000, eoa 258883.
- **Tensor names (confirmed by M0-4, `tools/reference/gemma/tensor_names.json`):** `model.language_model.{embed_tokens,norm}`,
  `model.language_model.layers.{i}.self_attn.{q,k,v,o}_proj` (no v_proj on full layers),
  `self_attn.{q_norm,k_norm}`, the four layernorms, `mlp.{gate,up,down}_proj`, `layer_scalar`;
  `model.vision_embedder.*`, `model.embed_vision.embedding_projection`, `model.embed_audio.embedding_projection`
  (prefixes confirmed by M0-4 / M0-5); there is no `lm_head` tensor (tied) and no `v_norm` tensor.
- **Known r4dx constraints:** attention kernels compiled per geometry (`third_party/libr4d/r4d.h`: only
  `h256_gqa6_fp8kv`, block 16); trellis needs N,K % 128; w4a16/bf16 GEMM fallback K % 512 (3840 fails,
  see 4.5); `ModelConfig::FromJson` requires GDN fields; `ModelConfig::Shard` forbids tied embeddings;
  converter hard-codes Qwen tensor names (`src/convert/main.cpp` ~1518-2042); RMSNorm kernels are (1+w)
  except `r4dx_rmsnorm_plain_bf16`; MLP is SiLU only (`gelu_tanh` exists for vision); single rope_theta;
  no softcap anywhere; BPE tokenizer rejects byte_fallback; server hard-codes `<think>`/`<tool_call>`.
- **Token / chat format:** thinking via `<|think|>` in the system prompt, output
  `<|channel>thought\n...<channel|>`; tools `<|tool_call>call:fn{...}<tool_call|>` with strings wrapped
  `<|"|>...<|"|>`; turns `<|turn>role\n...<turn|>`, assistant role `model`.

## 3. Design: text model, attention, KV cache, kernels (TP=1 first, then TP=2)

### 3.1 Verified facts and UNVERIFIED items

Verified in the repo:
- `TextModel::Config()` is only used for `hidden_size` (`src/cli/main.cpp:598`) and
  `num_hidden_layers` (`src/server/server_args.h:37`), so a thin `ModelConfig` mapping is enough.
- `ModelConfig::FromJson` hard-requires GDN fields (`model_config.h:159-162`) and `Container::Load`
  calls it unconditionally (`container.cpp:687, 1327`): Gemma needs its own container and config parser.
- `LoadTextModel` (`tp_model.cpp:1147`) is the single factory and the dispatch point. `TpModel` holds
  `std::optional<Model>`, so it cannot be reused for Gemma unchanged.
- libr4d attention is templated on `<NWARPS, TILE, HEAD_DIM, GQA, BS, KVP, OPT, SPLIT, DSPLIT>` with no
  window parameter. `AttentionLayer` hard-codes `scale = 1/sqrt(D)`, the q|gate split and mrope.
- `tests/kernels/*` call `hipSetDevice(0)`: every kernel test is GPU work and needs approval.

Settled by M0-5 (every item is VERIFIED against the HF source in docs/gemma4-semantics.md; each is still
gated by a rung-3 golden):
- `v_norm` is applied on every layer's V (sliding: `v_proj`; full: the raw `k_proj` output, before `k_norm`
  and rope); no `v_norm` tensor exists.
- `scaling = 1.0`.
- Embed scale is `sqrt(3840)` cast to the weight dtype: in bf16 that is **62.0**, not 61.968.
- Sliding mask is `dist < sliding_window` (a query sees 1024 keys including itself).
- **Image-token bidirectional masking: sliding layers only** (full layers stay causal; the generate path and
  the HF docstring agree, a bare `forward()` with `mm_token_type_ids` differs on the 8 full layers: the
  reference must use the mask dict of `generate`). The attention hook (`klimit_ext`) is built into the
  sliding kernel in M1 so M2 needs no kernel rework.
- Proportional rope pair layout (rotate pairs `i, i+256` for `i<64`, identity elsewhere; frequency
  denominator 512).
- `layer_types` (parse generically, assert the 5:1 pattern with full at 5, 11, ..., 47).
- **`layer_scalar` placement:** HF applies it once per layer after the MLP residual add; the buffer is bf16
  `[1]`. The fused post-norm kernel takes a scalar; the attention-half call MUST pass 1.0 and the golden
  pins this.
- **BOS:** HF adds no BOS to raw text (`tok("hi").input_ids == [2202]`); `<bos>` appears only as text in
  the chat template. KL tokens add BOS=2 explicitly on both sides.
- **Final softcap** is applied by HF to the lm_head output in its own dtype (bf16 for the bf16 model).
- `max_position_embeddings` (131072 Huihui, 262144 google) is metadata only: no rope scaling exists.

### 3.2 Architecture dispatch and TextModel fit

- New `src/model/gemma_config.h`: `GemmaConfig` (hidden, layers, `layer_types`, heads 16, kv sliding 8,

  full) and down (7680 = 15 x 512); vocab % (16*world); **tie allowed**.
- New `src/model/arch.h/.cpp`: `enum class Arch {kQwen35, kGemma4}`, `DetectArch(container_path)` reads
  only `__metadata__.model_config` (`model_type` / `architectures`). `LoadTextModel` calls it first;
  Gemma goes to `LoadGemmaTextModel`, the Qwen branches stay byte-identical.
- Classes: `GemmaModel` (`gemma_model.{h,cpp}`, single-device engine), `GemmaLocalTextModel`
  (TP=1 wrapper), `GemmaTpModel` (later).
- TextModel method map: Prefill / PrefillMultimodal / DecodeStep / Greedy / Sampled / Reset /
  SaveCheckpoint / RestoreCheckpoint implemented; `DecodeStepMtp*` throw `core::TpUnsupportedError`
  and `MtpEnabled()` is false; `DecodeStepDflash*` via `VerifyWindow` / `CommitVerifiedWindow` (drafter
  track; captures inverse-rotated when rotation is on); `*Profiled` implemented; vision hooks owned by
  M2 (`GemmaModel` only exposes the splice point).
- Why not a flag in `Model`: `Model::Load` (~420 lines) and `RunChunk` are full of GDN, mrope, MTP and
  64-row-slice logic. Accept duplication of the sampling/verify helpers at first and dedupe after the
  TP=1 KL gate passes.

#### Forward structure (`GemmaModel::RunChunk`, T <= 256, no GDN/MTP)
1. Scaled embedding gather (device-resident table, always on, 2 GB).
2. Splice image/audio rows over the gather result (unscaled).
3. Optional `RotateResidual` forward.
4. Per-chunk metadata: `positions[T]`, `seqused_k`, `slots_ring[T]` (= `(pos+t) % ring_tokens`), and an
   optional `klimit_ext[T]` for bidirectional image blocks.
5. 48 layers of `GemmaLayer::Forward` (sliding or full geometry per `layer_types`).
6. Optional inverse rotation, final norm, tied lm_head, softcap.

Bidirectional image block: a per-query absolute key-limit override array (null for text). An image
block of 280+2 tokens exceeds a 256-row chunk, so the chunk planner makes an image block its own chunk
of up to 288 rows; size `buf_a_`, `buf_b_` and the arena for 320 rows (M2 decision).

### 3.3 Attention

| | Sliding (40 layers) | Full (8 layers; TP=1 / TP=2 rank) |
|---|---|---|
| q / kv heads / gqa | 16/8/2 -> 8/4/2 | 16/1/16 -> 8/1/8 |
| head_dim | 256 | 512 |
| V source | v_proj (+ v_norm, flag) | k_proj output, K = V |
| rope | theta 1e4, full 256, pairs i<->i+128 | theta 1e6, pairs i<->i+256 for i<64 |
| mask | causal and `kpos > qpos-1024` | causal |
| KV store | ring of 1536 tokens | full context |
| fp8 KV per token | 8*512 B = 4 KiB | 1*1024 B = 1 KiB |

Common: no q gate, scale 1.0, no softcap inside attention, plain `q_proj`. `AttentionLayer` is not
reused; add `GemmaAttnLayer` (`gemma_attention_layer.hpp`) with its own config/weights.

#### Sliding KV ring by block-table aliasing (no kernel addressing change)
- Kernels address keys as `bt[kk/16]`. One shared int32 table `T[i] = i % RB` for
  `i < ceil(max_ctx/16)` (16384 entries, 64 KiB) serves all 40 sliding layers; physical storage is RB = 96
  blocks (1536 tokens). Write slot `pos % 1536` equals `((p/16)%96)*16 + p%16`, so
  `r4dx_kv_write_paged_fp8_hnd` is used unchanged with a ring slot array.
- Safety: a chunk writes `[pos, pos+T)` before attention and the earliest query reads `pos-W+1`.
  Required `RB*16 >= W + T` (1024 + 288 <= 1536; slack 512). Verify windows (<=16) and image chunks
  (<=288) fit.
- Tile over-read: kernels load tiles that may start below the window (up to 47 keys); those slots alias
  newer keys but are always finite fp8 (the cache MUST be zero-initialised) so masked P=0 x V stays 0.
- Memory: 40 x 8 x 1536 x 512 B = **252 MB** fp8 (503 MB bf16).
- Speculative rollback is safe within the slack. `SaveCheckpoint` D2D-copies the 40 rings (252 MB,
  ~1 ms) into a spare; full-layer KV needs no copy (position overwrite). Net +252 MB.
- New files: `sliding_kv_cache.hpp`; a host+device pure header `r4d_attn_window.h` (CPU-testable).
- **Critique note:** the existing KL corpus segments are exactly 1024 tokens, so the ring never wraps
  there; a 1536+ token long segment is added (M0-7).

#### Kernel plan (staged so correctness is not gated on perf kernels)
- **Stage 0, correctness oracle (r4dx-owned):** `src/model/attention/src/attn_ref.hip`
  (`r4dx_gemma_attn_ref_bf16kv/fp8kv`), generic over head_dim <= 512, gqa, window, scale, causal +
  `klimit_ext`, fp8/bf16 KV, ring table; fp32 two-pass softmax, one workgroup per (query, q-head), no
  WMMA. Slow at long context but unblocks rung-3 goldens and the KL gate independently of libr4d work.
  Plus a CPU fp32 reference in tests.
- **Stage 1, sliding `h256_gqa2` with window (libr4d):** new TU `r4d_attn_paged_h256_gqa2.hip` including
  the existing prefill/decode templates (already parametric in GQA). New template params `bool WIN`,
  `bool EXT` (default false so Qwen instantiations compile identically): lower bound
  `kpos >= klimit - W + 1` in the mask select; tile start `t_lo = max(klow_cta,0)/TILE`; decode `t0`
  shift mirrored in the split-KV combine's `u` formula; for EXT `klimit = max(klimit, klimit_ext[qpos])`.
  Extra args in `R4DArgsW { R4DArgs base; int window; const int* klimit_ext; }` so `R4DArgs` is
  unchanged. Prefill NWARPS 8, TILE 48; decode serves q_len <= 32; decode split law uses
  `max_ctx = min(ctx, W + q_len + 16)`. Entry points `r4d_attn_{prefill,decode}_h256_gqa2_fp8kv` and
  `..._scratch_bytes`.
- **Stage 2, full `h512_gqa16` / `gqa8` (libr4d), the real kernel risk:** direct HEAD_DIM 512
  instantiation does not fit registers (`qf[32]` = 128 VGPR, `acc[32]` = 256 VGPR vs ~190 budget). Design:
  within-workgroup D-split (`NWR` row-waves x `DS` d-slice waves; each d-slice recomputes QK for the same
  16 rows, owns 512/DS output columns; K/V staged once in LDS); start DS=4, fall back to DS=8. Use the
  split-KV prefill kernel (`SPLIT=1`) plus the existing combine kernel for decode and verify
  (q_len <= 8) instead of a new h512 decode kernel. Plain prefill NWR = 8 as a starting point (tune).
  Expected cost at 262k (estimate): decode reads ~268 MB of K per full layer per token, 8 layers ~
  2.1 GB/token ~ 3.4 ms; full-context prefill attention minutes. Fallback: `KVP=1` (bf16 KV) fits LDS at
  TILE 16; bf16 KV for the 8 full layers costs 4.3 GB at 262k.
- **Registration plumbing:** add units to `R4D_UNITS` and `R4D_DEPS_*` in `third_party/CMakeLists.txt`,
  rows in `r4d_registry.hip`, bump `R4D_VERSION` to 0.6.0, wrappers in `r4dx/core/r4d.hpp`,
  `r4d_attn_geom_count()/geom_at(i)` for multi-geometry validation at load. **Qwen-unchanged guard
  (build-only):** a CMake step like `check_trellis_isa` that compiles the Qwen attention unit with
  `--cuda-device-only -S` before/after and diffs the listing.

### 3.4 RoPE

- Sliding: reuse `r4dx_rope_neox_bf16(..., head_dim=256, theta=1e4)`; verify at a golden.
- Full: new kernel `r4dx_rope_proportional_bf16(q, k, pos, tokens, Hq, Hk, head_dim, n_pairs, freq_dim,
  theta, stream)` (full layer: 512, 64, 512, 1e6). It also expresses sliding (128 pairs, freq_dim 256) so
  a CPU test can cross-check. Dims not in a rotated pair pass through. No mrope; images use plain 1-D
  positions (UNVERIFIED).

### 3.6 fp8 KV calibration and risks

- `r4dx_convert::ResolveKvDescale` is architecture-neutral; container tensors
  `text.layers.{i}.attn.{k,v}_descale` fp32[kv_heads] (8 sliding, 1 full). Verify the converter's layer
  loop does not assume uniform `kv_heads`.
- `kv_calibrate_full.py` is Qwen-specific; port under the new venv, capturing post-rope K and V as
  cached (for k_eq_v: `v_norm(raw k_proj)`), per-layer-type head counts, long (>1024 token) sequences.
- **Main risk:** scaling 1.0 means q_norm/k_norm weights carry the 1/sqrt(d) factor; QK logits may be
  large and fp8 K error proportionally larger. Run the fake-quant study BEFORE h512 kernel work. If full
  layers dominate, use bf16 KV for the 8 full layers only (open question 5). Also check
  `|q*mul| < 65504` and f16 subnormals in the fold (`FOLDQ`).

### 3.7 Linear paths, shapes, memory

GEMM shapes (N x K) at TP=1: sliding q/k/v/o 4096x3840, 2048x3840 (x2), 3840x4096; full q/k/o 8192x3840,
512x3840, 3840x8192; gate_up 30720x3840; down 3840x15360; lm_head 262144x3840.
- Trellis: all N and K are multiples of 128. `FallbackTuning` halves SKG until `(K/16) % (SK*SKG*U) == 0`.
  No tuning rows exist yet, so the fallback runs until `tool_trellis_gemm_bench` is run (GPU). Confirm
  `PlanTrellisM256` per shape; a failed plan silently falls back to 64-row slicing.
- **bf16/w4a16 fallback fails today:** `FallbackTuning` throws for `K % 512 != 0` (`linear.cpp:99`). The
  kernels' own rules need only K % 256 at SK=4 (3840 = 15 x 256). **Change:** relax to `K % 256`; Qwen
  picks are unchanged. Do NOT add K-padding (rejected alternative).
- `PickTuning` key (N<<28 | K<<8 | M) holds N=262144, K=15360.
- TP=2 per rank: sliding q 2048, k/v 1024, o K=2048; full q 4096, k 512 (replicated), o K=4096; gate_up
  15360x3840; down K=7680. All pass the existing rules; all-reduces stay at two per layer.
- Tied lm_head under TP: `GemmaConfig::Shard` allows tie; rank r takes rows `[r*131072, (r+1)*131072)`
  (v1 copies the slice, 1 GB bf16 per rank). `tp::RuleFor` learns Gemma names.
- lm_head cost: bf16 table read is 2 GB/token (~3 ms, ~25% of a trellis decode step); consider a trellis
  copy for the lm_head only, keeping the bf16 table for embedding gathers.

Memory budget at TP=1, 262144 context:

## 4. Design: converter, container, trellis quant, rotation

### 4.1 Decisions that need attention

1. **Trellis and rotation.** For Qwen `--trellis-from` still throws unless `--rotate none`
   (`docs/quant2.md` 7.1 says trellis incoherence processing replaces q2ab; the default Qwen trellis
   container is unrotated). For Gemma they combine (section 10): the oracle quantizes the folded weights
   against the rotated Hessians and the converter checks the oracle's rotation fingerprint and verifies
   against fold(W). Generalizing rotation to 3840 was cheap CPU work (`rotation.hpp` is parametric in
   `(block, nblk)`) and is done with tests; the Gemma rotation **runtime** is part of M1, not conditional
   (section 9.7, M1-31).
2. **Post-norms block the Qwen fold.** Out-projections cannot take `W' = Q^T W` (see 4.4).
3. **K=3840 is not a kernel problem** (see 3.7): relax `FallbackTuning` to K % 256.
4. **The converter cannot read the checkpoint yet:** C++ `ShardedModel` requires
   `model.safetensors.index.json` (`safetensors_reader.hpp:184-186`); Huihui is a single
   `model.safetensors`. Python `ShardIndex` handles single-file but `trellis_quant.py:1332` does not.
5. **The Python capture/oracle stack is Qwen-specific** (`StreamingReference`, `hessian_capture.py`,
   `imatrix_capture.py`, `kv_calibrate*.py`, `trellis_quant.py`): one shared Gemma reference package plus
   an arch table, not a fork per script.

### 4.4 Rotation: generalizing to 3840 and what folds

Hard-coded today: `kRotationBlock = 1024` default, `main.cpp:957` (`hidden != 5*1024`),
`rotation_meta.h:36-37, 67, 118-125`, `docs/container-format.md`, and the kernel
`r4dx_rotate_residual_bf16` (5 x 1024). Changes: `ChooseRotationBlock(hidden)` = largest power of two
dividing hidden, capped 1024 (5120 -> 1024 / nblk 5 identical bytes; 3840 -> 256 / nblk 15); metadata
gains `"nblk"`; new containers write `rotation.mix` [nblk, nblk] (Qwen keeps `rotation.mix5`). Gemma q2ab
Hadamard sites: `down` (K=15360, block 512), `o_swa` (K=4096, block 256), `o_full` (K=8192, block 256),
each with its own sign tensor; `HadSite` gains `kOSliding`/`kOFull`. Extend `tests/convert/test_rotation.cpp`
(`convert_rotation`) with hidden 3840/block 256 and 768.

What folds: `input_layernorm` -> q/k/v and `pre_feedforward_layernorm` -> gate/up fold as
`W' = W diag(w) Q` with a **plain** weight (add `norm_offset`, Qwen 1.0 / Gemma 0.0, to `FoldRowsQ`,
`TransformHessianQ`, `TransformImportanceQ`, `CheckNormInvertible`). `final_norm`/lm_head need no fold
(`x Q^T` is applied before final_norm). `post_attention_layernorm` / `post_feedforward_layernorm` do NOT
fold (`Q^T` does not commute with the channelwise weight); `layer_scalar` commutes.

**Contract (option A, chosen; both sections' conflict resolved in its favour):** o_proj and down_proj get
only `W Hb` on the K side (`LinearFold::kHadOnly`); their outputs stay in the original basis; the runtime
fuses `post_norm(plain w) -> rotate Q -> residual add (-> layer_scalar)` (kernel `post_rmsnorm_rotate_add`,
block 256 / nblk 15): one transform per sublayer. Option B (online `Q^T -> w -> Q`, two transforms) is
rejected. Embedding: gather, scale (text rows only), splice vision/audio, then `x Q`; un-rotate before
final_norm and before DFlash captures. Option A is numerically verified by the numpy selftest (M1-5,
`tools/reference/gemma/rotation_selftest.py`). Rotation reaches the w4a16 path and, via section 10, the
trellis path; the runtime (fused kernel, entry/exit ops) is M1-31, in M1 (section 9.7).

## 5. Design: tokenizer, chat template, server

### 5.1 Findings that change the plan

1. **tokenizer.json is not the spec we were given.** It is identical in google and Huihui repos (sha256
   `cc8d3a0c...bfe0f`, 32,169,626 bytes). `normalizer` = `Replace(" " -> "▁")`; `pre_tokenizer` =
   `Split(" ", MergedWithPrevious)` (a no-op after the normalizer); no Metaspace, no regex; BPE with
   `byte_fallback=true`, `ignore_merges=false`, 262144 vocab, 514,906 merges; decoder
   `Sequence[Replace ▁->" ", ByteFallback, Fuse]`; no automatic BOS.
2. **The newline-run rule is a safe optimization, not a semantic requirement.** No vocab entry or merge
   mixes `\n` with other characters; newline runs have 31 entries (1..31) and BPE equals "greedy chunks of
   31 then remainder" (verified 1..199 newlines and `▁` runs). Its source is probably the transformers
   `GemmaTokenizer` runtime class, so the golden generator MUST produce raw-`tokenizers` and `AutoTokenizer`
   ids and assert they agree (Qwen had exactly this override trap).
3. **All 24 added tokens are `special`**, so `make_stream_decoder(skip_special_tokens=true)` would erase
   `<|channel>`, `<channel|>`, `<|tool_call>`, `<tool_call|>`, `<|"|>` before the splitter/parser sees
   them. A decode keep-list is required.
4. **minja cannot load the Gemma template as is.** (a) adjacent string literals at template lines
   258-262 are unsupported (`ChatTemplate::from_source` throws); (b) caps probing yields
   `supports_tool_calls=false`, and the default polyfills would rewrite assistant `tool_calls` into JSON
   content, destroying the Gemma tool format: polyfills MUST be off for Gemma; (c) `dictsort` is
   byte-wise, Jinja's default is case-insensitive. Three local patches to `third_party/minja/minja.hpp`
   with notes in `third_party/VERSIONS.md`.
5. **EOS is `[1, 106, 50]`** from `generation_config.json` (open question 4), plus `suppress_tokens`
   `[258883, 258882]` needing a sampler logit mask (non-blocking).
6. **Thinking semantics differ from Qwen.** Qwen's prompt ends `<think>\n` (splitter starts in
   reasoning). Gemma thinking on: prompt ends `<|turn>model\n` and the model generates
   `<|channel>thought\n...<channel|>`; thinking off: template appends an empty `<|channel>thought\n<channel|>`;
   after a tool response with thinking on the prompt ends `<|channel>thought\n`; history stripping is done
   by the template. `<bos>` is emitted by the template as text: encode with `parse_special=true`, do not
   add it twice.

8. **BOS in the KL corpus:** BOS=2 first on both sides.
9. **EOS set:** `generation_config.json` gives `[1,106,50]` (deviation from the brief; open question 4).

kernels, preprocessor, 288-row chunk planner, `EncodeImages`, API content parts, `image_prompt.h`
expansion), so M2 and M3 start with a design pass; whether libr4d is editable at all is open question 2.

Decided with the user on 2026-10-01. These override anything earlier in this doc.

1. **Context length.** The default is 131072, taken from Huihui's config. 262144 is opt-in through a flag.
2. **libr4d.** Extend `third_party/libr4d` with `WIN`/`EXT` template parameters and new translation units. The Qwen instantiations must stay bit-identical.
3. **Device rule.** Add the `R4DX_REF_ALLOWED_DEVICES` env override. The default stays device 1.
4. **EOS ids.** Use `[1, 106, 50]`, following `generation_config.json`.
5. **fp8 KV fallback.** Allowed only if the KL gate fails: the 8 full layers then use bf16 KV. Sliding layers stay fp8.
6. **Torch.** The new venv may use a newer ROCm torch wheel. Python312 stays untouched.
7. **Rotation.** Generalize it fully in M1, the runtime fused post-norm-rotate-add kernel included. Rotated trellis Gemma is run and measured against the KL gate in M1.
8. **Drafter training data.** Prompts are 20–100K subsampled from Nemotron Post-Training v2 and CodeAlpaca. Responses are generated by Huihui-Gemma through r4dx once M1 passes. Trellis calibration data still comes from HF on the existing 385-prompt corpus (M0-9).
9. **KL gate = fp32 truth, noise-relative.** bf16 HF is not a stable yardstick for Gemma 4: the residual stream reaches 100-300 (L9-L40) and bf16 rounding is amplified (position 1 at L10, full layers L23/L29/L41). Measured on English raw text against the fp32 truth: HF bf16 sdpa KL 0.05 (top-1 96%), HF bf16 eager KL 0.23 (top-1 87%); fp32 eager == fp32 sdpa (KL 9e-9), so there is no reference bug (`tools/reference/gemma/investigate/`). The M1 gate is therefore: per sequence group, `KL(fp32 || r4dx) <= 1.5 x KL(fp32 || HF-bf16-sdpa) + 0.005` (mean over scored rows) and `top-1(fp32, r4dx) >= top-1(fp32, HF-bf16-sdpa) - 1 pt`; median and p99 KL and the worst rows are reported too. For quantized (trellis) containers the 0.01 target applies to the INCREMENT over the r4dx bf16 container, `KL(fp32||quant) - KL(fp32||r4dx-bf16) <= 0.01`, not to the absolute KL. Tool: `kl_report.py --gate gemma-fp32 [--base-dir <r4dx bf16 dump>]`; the truth and noise dumps are in `D:\models\r4dx\huihui-gemma\kl\fp32\{truth,bf16sdpa}` (made on CPU by `full_logits_gemma_cpu.py`).
10. **Gate corpus.** PRIMARY: `tools/reference/kl_corpus/chat_gemma.json`, 10 chat-templated sequences (8 thinking off, 2 thinking on; English, Thai, Python, C++; one user turn plus a natural model answer, rendered with the Gemma chat template, BOS once), scored on model-turn tokens only through the per-token `score_mask` (thinking on: thought span and answer; both include the closing `<turn|>`). Gate groups are english, thai, code (python + cpp) and the pooled chat-ALL; every group must pass. SECONDARY: the raw segments of `tokens_gemma.json` (cpp_source, thai_prose, english_prose, python_source) truncated to 512 tokens, reported with no pass/fail: raw BOS-only text is off-distribution (ppl 200-1000 for both Huihui and official Gemma; chat model-turn ppl is ~13), so it measures noise amplification rather than model quality. r4dx runs must score the same ids (raw truncated to 512).
11. **r4dx Gemma keeps its residual stream in fp32.** GEMM inputs stay bf16 (or quantized); only the residual accumulator and its adds/norm inputs are fp32. This removes the bf16 residual rounding that dominates the noise above. Old bf16 eager KL references (`kl\ref`, `kl\ref-noise`, `kl\ref-long`, `kl\ref-long-noise`) are DIAGNOSTIC ONLY and must not be used as a gate; the gate references are the fp32 dumps of item 9.

   Measured noise term (HF bf16 sdpa, hf-bf16 lm_head, vs fp32 truth, chat corpus, model-turn rows; `fp32\noise_term.json`) and the resulting gate thresholds:

   | chat-thai | 1003 | 0.00087 | 0.00004 / 0.0076 | 98.50% | 0.00630 | 97.50% |

## 10. Rotated trellis, and the quantization tool ports (branch g4-convert-trellis)

Decisions taken while implementing M1-25 / the M1-28 prerequisites. They refine 4.4 / 4.5 and section 9.7.

### 10.1 Converter: `--trellis-from` on Gemma

- The oracle manifest is keyed by HF tensor names, which is all `trellis_import.hpp` reads; every Gemma body
  base starts with `text.layers.`, so the import is Qwen's code unchanged. The oracle must not list a `v_proj`
  for a full layer (k_eq_v; a stray entry is reported as unused, never imported) and must cover every other
  linear (a missing one is refused before an output exists).
- The tied `lm_head` is not a body linear: it stays on the w4a16 path. Command shape (the linear is LDLQ'd
  against `lm_head.hess`, captured at the post-final-norm hidden before the softcap):
  `r4dx-convert --input <huihui> --output <out> --trellis-from <oracle-dir> --kv-calib <kvcalib.json> --no-bf16 --lm-head w4a16 --w4a16-group-rule "^lm_head$=32" --hessian-dir <hessian-v1> --ldlq "^lm_head$"`
  (`--no-bf16` is needed because a group rule refuses a linear that also keeps a bf16 companion).
- `--kv-calib` already worked for Gemma (per-layer head counts, 8 sliding / 1 full); `convert_gemma_trellis`
  covers it with a trellis container.

### 10.2 Rotated trellis: how the oracle's basis and the converter's agree

Decision: **the oracle quantizes the folded weights against the rotated Hessians; the converter is the single
source of truth of Q.**

1. `r4dx-convert --input <huihui> --rotate q2ab [--rotation-seed S] --rotation-out rot.safetensors` writes
   only the fp32 rotation tensors (`rotation.signs`, `rotation.mix`, `rotation.had_down_signs`,
   `rotation.had_o_signs`, `rotation.had_o_full_signs`) plus a fingerprint `{kind, seed, tensors_sha256,
   hidden, block}` (sha256 of `"r4dx-rotation-v1\n"` + per tensor name, u64 count and fp32 bytes) and exits.
   The oracle never re-derives Q from the seed.
2. `trellis_quant.py quantize-model --arch gemma4_unified --rotation rot.safetensors ...`
   (`tools/reference/rotation_oracle.py`) folds each shared-Hessian group before quantizing it:
   - in-projections (q, k, v, gate, up): `W' = (W diag(w_norm)) Q` with the PLAIN norm weight (offset 0) of
     `input_layernorm` / `pre_feedforward_layernorm`; Hessian `H' = Q^T H_rms Q` from the weightless rms tap
     (`hessian_capture.py --rms-taps`, `hessian.json` `rms_keys`), else `Q^T D^-1 H D^-1 Q` from the post-norm
     tap (refused where `|w| < 1e-3`);
   - out-projections under q2ab (Gemma option A): `W' = W Hb` with `H' = Hb^T H Hb`; under q2a they are not folded;
   - `lm_head`, embeddings and norms are never folded.
   The manifest (and every per-layer record, so resumption is keyed on it) carries `rotation` = the file's
   fingerprint and `arch`.
3. `r4dx-convert --rotate q2ab --trellis-from <oracle>` refuses a manifest whose fingerprint is not this run's
   (kind, seed, tensors_sha256), refuses a rotated manifest without `--rotate` and an unrotated one with it, and
   its reconstruction check compares against `fold(W)` (per 128-row block, the converter's own fold), not W.
   Qwen keeps the `--trellis-from needs --rotate none` refusal. The result is recorded in
   `r4dx_convert_run.trellis.rotation`.
4. The folded norms are stored as ones under `.rotated`, the container carries `rotation.*` tensors and
   `__metadata__.rotation` (`out_fold: had_only`), exactly as a w4a16 rotated container does.
5. **Runtime:** the Qwen loader refuses trellis with rotation; the Gemma loader (M1-19) must accept the pair
   (the trellis kernel's own RHT runs on the already-rotated activation, which is exact) and the M1-31 entry /
   exit ops apply. Not done here (no GPU, no loader yet).

Tests: `convert_gemma_trellis` (all C++, CPU: plain, q2ab, q2a, every refusal), `reference_arch_gemma` (the
Python oracle against the converter end to end on a tiny checkpoint: its fold equals the converter's folded
bf16 bytes, its manifest is imported and verified by `r4dx-convert`), `test_tp_shard` (row split of
`rotation.had_o_full_signs`).

  `reference_hessian_rms` and `reference_trellis_quant` pass). Gemma taps: `in` (q/k/v input; no v on the 8 full
